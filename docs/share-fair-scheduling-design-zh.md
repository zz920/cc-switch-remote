# TokenTap 共享网络公平调度设计草案

## 1. 文档目标

本文用于确认共享网络调度的前置约束、问题模型和推荐实现路线。它描述的是后续设计，不代表当前版本已经实现评分调度。

当前版本继续保留用户可见的四种路由偏好：`local_only`、`local_first`、`network_first`、`network_only`。公平调度只负责在同一优先级内选择候选节点，不能越过用户明确设置的本地/网络边界。

## 2. 当前实现与已确认事实

1. 一个 TokenTap 实例当前只能加入一个共享网络。共享网络配置保存为单实例记录，网络身份和密钥也只有一套。
2. `creator` 和 `member` 是网络管理角色，不是流量角色。当前技术结构允许同一节点同时提供 API 和消费其他节点的 API。
3. 远端节点不会作为普通供应商写入本地供应商数据库。消费端按“远端节点 + 应用”生成运行时共享供应商，例如 `share:<peer_id>`。
4. 当前共享路由只适用于真正经过本地代理接管的应用：Claude、Codex、Gemini 和 GrokBuild。
5. 一个远端节点可为同一应用暴露多个本地供应商；第一阶段由远端节点负责其内部供应商选择，网络调度器只选择远端节点。
6. 当前远端候选顺序没有网络质量或公平性语义，不应依赖容器或 `HashMap` 的遍历顺序。
7. P2P 直连是首选链路；Relay/TCP 是可用性兜底。连接方式应参与评分，但 Relay 节点不能仅因不是直连而被永久排除。
8. Token 统计以成功请求为准，成本为输入、输出、缓存读取和缓存创建 Token 之和。失败请求仍应记录健康指标，但不计入已提供/已消费 Token。

## 3. 建议先确定的产品约束

| 问题                                  | 推荐约束                                         | 原因                                           |
| ------------------------------------- | ------------------------------------------------ | ---------------------------------------------- |
| 一个实例能否加入多个网络              | 第一阶段维持一个实例一个网络                     | 简化身份、密钥、审批、统计和路由边界           |
| 节点能否同时作为 Provider 和 Consumer | 允许同时承担两种流量角色                         | 更符合点对点共享；管理角色不应限制业务能力     |
| 是否建立独占的节点连接                | 不建立；每个请求独立选择一个节点                 | 便于故障切换和公平分配；流式请求建立后保持粘性 |
| 调度粒度                              | 先按“应用 + 远端节点”调度                        | 避免消费端感知或泄露远端供应商密钥与内部配置   |
| 公平性的计量单位                      | 以实际 Token 成本为主，不按请求数                | 不同请求成本差异很大，按请求计数容易失真       |
| Provider 是否必须显式共享             | 必须显式选择供应商，并可配置配额                 | 防止用户无意中承担费用                         |
| 网络供应商是否默认启用                | 新建/加入网络后默认 `local_only`                 | 必须由用户主动开启消费远端 API                 |
| 是否允许请求中途换节点                | 响应首字节前可以重试其他节点；响应开始后不可切换 | 避免流式响应重复、乱序和重复计费               |

如果未来支持多网络，应先增加网络维度的身份、密钥、路由策略和统计主键，不能直接在现有单网络记录上叠加数组。

## 4. 调度目标

调度器需要同时满足以下目标，优先级从高到低：

1. **正确性与安全边界**：只选择在线、未拉黑、已获批准、确实共享当前应用且未超过配额的节点。
2. **尊重用户策略**：严格执行本地优先、网络优先、仅本地或仅网络。
3. **可用性**：快速避开超时、429、5xx、连接失败或桥接异常的节点。
4. **网络质量**：优先低延迟、低首 Token 时间、较高成功率和 P2P 直连节点。
5. **公平性**：健康节点都有与其质量和容量相称的服务机会，不能由最高分节点长期垄断。
6. **稳定性**：短时抖动不能导致候选顺序频繁翻转。
7. **可解释性**：用户和日志能够说明某次选择是由健康、质量、配额还是公平债务决定。

这些目标不包含跨用户的经济结算或“贡献多少才能消费多少”。如果需要贡献积分或代币经济，应作为独立的信用/结算层设计，不能混入网络质量分数。

## 5. 候选过滤

评分前必须先执行硬过滤。对应用 `a`，节点 `i` 只有同时满足以下条件才是候选：

```text
eligible(i, a) = approved
              && online
              && !blocked
              && bridge_healthy
              && shares_app(i, a)
              && quota_remaining(i, a) > 0
              && circuit_breaker(i, a) != OPEN
```

`local_first` 和 `network_first` 应实现为候选层级，而不是把本地与网络候选混合后统一评分：

- `local_first`：本地层存在健康候选时不进入网络层。
- `network_first`：网络层存在健康候选时不进入本地层。
- `local_only`：不创建共享候选。
- `network_only`：本地候选不参与业务请求，但管理、探活和恢复不受影响。

## 6. 观测指标

评分尽量使用消费端本机观测值，避免信任 Provider 自报的延迟或成功率。

每个“网络 + 应用 + 节点”维护以下滚动指标：

- 最近一次在线时间和连续失败次数；
- 请求成功率，以及连接失败、超时、429、5xx 的分类计数；
- P2P 握手/探活 RTT；
- 首 Token 时间（TTFT）和总响应时间；
- P2P 直连或 Relay/TCP 连接方式；
- 当前进行中请求数；
- 最近窗口内实际消费 Token；
- 配额剩余量和熔断状态。

延迟、TTFT 和成功率采用 EWMA，避免单次抖动立即改变路由：

```text
ewma_new = alpha * sample + (1 - alpha) * ewma_old
```

初始建议 `alpha = 0.2`。连接失败应立即增加失败计数，但恢复需要连续成功样本或半开探测，防止节点在开/关状态间抖动。

## 7. 质量分数

所有指标归一化到 `[0, 1]`，得到基础质量分：

```text
quality_i = 0.35 * success_i
          + 0.25 * ttft_i
          + 0.15 * rtt_i
          + 0.10 * latency_i
          + 0.10 * connection_i
          + 0.05 * availability_i
```

其中：

- `connection_i`：P2P 直连取较高值，Relay/TCP 取较低但非零值；
- 429 应主要降低容量/负载得分，连接失败和 5xx 主要降低健康得分；
- 新节点使用保守先验分数并获得少量探索流量，不能因“没有历史”永久没有请求；
- 分数只用于形成权重，不能直接采用“永远选择最高分”。

上述权重是初始值，必须通过影子数据验证后调整，不应成为不可配置的业务常量。

## 8. 推荐算法：过滤 + 熔断 + Token 公平队列 + 质量权重

推荐采用分层方案，而不是单一综合分数：

1. 用硬约束过滤不可用节点。
2. 用熔断器快速隔离连续失败节点。
3. 将质量分和用户配置容量转换为有效权重。
4. 使用加权赤字轮询（Weighted Deficit Round Robin，WDRR）按 Token 成本分配请求。
5. 当两个候选赤字接近时，选择进行中请求更少或当前延迟更低的节点。

有效权重可表示为：

```text
effective_weight_i = configured_capacity_i
                   * clamp(quality_i, 0.1, 1.0)
                   * recovery_factor_i
```

每轮按有效权重增加节点赤字。请求发送前使用预测 Token 或固定基础成本预扣；请求结束后用实际 Token 修正：

```text
deficit_i += quantum * effective_weight_i
deficit_i -= actual_token_cost
```

预测成本不可靠时，可先按固定成本选择节点，结束后按实际 Token 结算赤字。必须限制赤字上限，避免长时间离线节点恢复后一次性获得过多流量。

这个方案的优点：

- 相比纯轮询，它能考虑网络质量和容量；
- 相比永远选择最高分，它不会饿死次优但健康的节点；
- 相比按请求数公平，它能处理短请求和超长请求的成本差异；
- 相比强化学习或全局最优化，它容易测试、解释和回滚。

不建议第一阶段采用：

- **纯最高分**：容易造成赢家通吃和分数抖动；
- **纯随机或纯轮询**：忽略失败率、延迟和节点容量；
- **依赖 Provider 自报分数**：容易被错误配置或恶意节点操纵；
- **强化学习/拍卖机制**：样本、可解释性和安全边界尚不成熟。

## 9. 熔断、重试与流式请求

- 连续连接失败、超时或 5xx 达到阈值后打开熔断器。
- 熔断冷却后进入半开状态，只允许少量探测请求。
- 429 使用较短冷却时间，并减少有效容量，不应与网络断线完全同等处理。
- 在尚未收到响应头/首字节时，可以切换到另一个节点，且同一次请求不能重复选择刚失败的节点。
- 一旦流式响应开始，固定使用该节点直到结束或失败。
- 自动重试次数必须有上限，并在日志中记录原始节点、失败原因和后继节点。

## 10. 建议代码结构

建议新增独立调度模块，不把评分逻辑继续堆入 `ConsumerRouteHook`：

```text
share/
  scheduler/
    mod.rs              调度入口和候选过滤
    telemetry.rs        EWMA、窗口统计和连接观测
    circuit_breaker.rs  熔断状态机
    wdrr.rs             Token 加权赤字轮询
    types.rs            候选、选择结果和可解释原因
```

建议职责边界：

- `ConsumerRouteHook`：根据路由偏好决定本地层/网络层，并请求调度器给出有序共享候选；
- `ShareScheduler`：过滤、评分、公平选择和失败反馈；
- bridge/transport：报告 P2P、Relay、RTT、连接失败等链路指标；
- proxy request log：报告状态码、TTFT、总时延和实际 Token；
- UI：只展示聚合状态和选择原因，不读取 Provider 密钥或请求内容。

热窗口状态保存在内存中；按小时/天聚合的数据可持久化。不要为每个探活样本同步写 SQLite，以免制造额外磁盘 I/O。

## 11. 分阶段落地

### 阶段 0：只采集，不改变路由

- 建立指标结构和事件接口；
- 记录 P2P/Relay、RTT、TTFT、状态码、Token 和进行中请求；
- 验证日志不会保存 API Key、Prompt 或响应正文。

### 阶段 1：影子评分

- 后台计算候选分数和模拟选择，但仍使用旧路由；
- 对比真实选择与模拟选择的成功率、TTFT 和分配比例；
- 在诊断页显示评分组成和被过滤原因。

### 阶段 2：功能开关下启用

- 对小规模网络启用熔断和 WDRR；
- 保留旧路由作为即时回滚开关；
- 设置新节点探索比例和最低服务份额。

### 阶段 3：容量和多供应商优化

- Provider 可配置并发容量和应用级额度；
- 评估是否需要消费端感知远端的多个供应商；
- 有足够数据后再调整评分权重和窗口长度。

## 12. 验收指标

1. 一个健康但质量略低的节点在长时间运行中不会获得零流量。
2. 流量比例在允许误差内接近有效权重比例，且按 Token 而不是请求数统计。
3. 节点连续失败后能在阈值内被熔断，恢复后通过半开探测平滑回归。
4. P2P 直连节点在其他条件相近时优先，但 P2P 不可用时 Relay 能继续服务。
5. `local_only` 不产生任何共享业务请求，`network_only` 不选择本地供应商。
6. 流式请求不会在响应中途切换节点或重复计费。
7. 调度日志能给出候选被过滤、被选择或被降权的原因。
8. 指标采集不记录密钥、Prompt 和响应正文。

## 13. 需要产品侧最终确认的问题

在编码评分调度前，需要明确以下四项：

1. 是否接受“同一节点可同时提供和消费”的推荐模型？
2. 公平性的目标是“消费端在多个 Provider 间公平分配”，还是还要加入“贡献与消费对等”的网络信用规则？
3. Provider 的容量权重由用户手动配置，还是第一阶段全部默认为 1？推荐先默认为 1，仅使用本机观测质量动态调整。
4. 是否接受只对 Claude、Codex、Gemini 和 GrokBuild 启用第一版调度，其他应用等具备本地代理接管能力后再加入？

以上四项确认后，可以据此拆分数据库迁移、遥测、调度器、UI 诊断和端到端测试任务。
